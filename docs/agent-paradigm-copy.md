# MindBridge 项目的 agent 范式说明文案

MindBridge 不是把一个大模型包成聊天框，然后让它直接回答学生的所有问题。它更像一套有边界的心理关怀工作流：学生发来一句话，系统先准备记忆，再判断这句话属于普通聊天、心理咨询还是高风险信号；如果需要心理支持，才进入知识检索和风险评估；最后由对应的回复 agent 组织给学生看的回答。模型参与了很多环节，但它不是唯一的决策来源，也不是随意行动的主角。

这就是本项目里 agent 范式最核心的取舍：不用一个万能 prompt 硬扛全部任务，而是把一轮对话拆成几个较小、职责清楚、可以审计的步骤。每个 agent 只做自己该做的事，每一步都留下记录，系统也随时可以用规则、词库、数据库和工具链兜底。对于校园心理健康场景来说，这种设计比“模型自己规划一切”更稳。它少了一些科幻感，但多了很多工程上的可信度。

## 1. 项目为什么需要 agent 范式

校园心理健康对话有一个很现实的矛盾：学生端需要自然、轻松、不会吓人的体验，后台又需要严肃地识别风险、记录报告和触发预警。如果把这些逻辑全部塞进一个 prompt，模型很容易在两个方向上摇摆。它可能把普通学习问题过度心理化，也可能在真正危险的表达里漏掉安全步骤。

MindBridge 用多 agent 把这件事拆开。普通聊天归普通聊天处理，心理求助才进入心理支持链路，高风险表达有额外的硬规则保护。学生看到的是一段自然回复，后台看到的是一条完整运行轨迹。这个分层很关键，因为心理关怀系统不能只追求“像人聊天”，还要能解释自己为什么这么判断、为什么查了某些知识、为什么生成了报告。

项目中的 agent loop 也不是开放式自主循环。它最多执行 8 步，并且 agent 的执行顺序由 `AgentRuntimeService` 固定。每个 agent 通过 `supports(context)` 判断当前状态是否轮到自己，执行后把结果写回 `AgentContext`。这更接近一个受控状态机，而不是让模型在黑箱里自由规划。

## 2. 一轮对话的基本路径

学生通过 `/api/chat/stream` 发起对话后，主流程先由 `ChatService` 接住请求。系统会拿到当前用户、会话、原始输入和脱敏后的模型输入。原始输入用于落库、报告和审计，脱敏输入用于模型侧处理，手机号、学号、身份证号、姓名等信息会被替换成占位符。

之后请求进入 `AgentRuntimeService`。运行时会按固定顺序寻找下一个可以执行的 agent：

```text
MemoryAgent
SupervisorAgent
KnowledgeAgent
RiskGuardianAgent
CompanionAgent 或 CounselorAgent
```

如果意图被判断为 `CHAT`，流程会在 `SupervisorAgent` 之后跳过知识检索和风险评估，直接交给 `CompanionAgent` 规划普通回复。如果意图是 `CONSULT` 或 `RISK`，系统会继续让 `KnowledgeAgent` 检索知识库，再让 `RiskGuardianAgent` 做后台心理状态评估，最后由 `CounselorAgent` 结合记忆、知识和风险结果生成回复策略。

最终回答仍由 `AiClient.stream()` 以 SSE token 流返回前端。也就是说，多 agent 负责规划、检索、评估和组装上下文，真正输出给学生的文字还是走统一的大模型流式生成。这个设计让前端体验保持顺滑，同时把后台判断过程拆开保存。

## 3. AgentContext 像一块共享工作台

`AgentContext` 是本项目 agent 范式里的共享工作台。一轮对话里的中间状态都放在这里，包括历史消息、记忆摘要、意图、知识库 query、检索结果、心理评估、风险等级、回复策略和最终要发给模型的消息列表。

它不是一个随便塞数据的 Map，而是有明确字段和标记位。比如 `memoryLoaded` 表示记忆是否准备好，`intentRouted` 表示意图是否已经分类，`knowledgeHandled` 表示知识检索是否完成，`riskAssessed` 表示风险评估是否完成，`responsePlanned` 表示回复策略是否已经生成。

这些标记位让流程非常直观。`MemoryAgent` 只在记忆没加载时执行，执行完把 `memoryLoaded` 标成 true。`SupervisorAgent` 只在记忆完成但意图没路由时执行。后面的 agent 也是一样。运行时不需要猜下一步，它只要扫描 agent 列表，找到第一个当前可执行的 agent。

这样的好处是边界清楚。一个 agent 不需要知道全部系统怎么运转，只要关注自己负责的上下文字段。系统要排查问题时，也能从 trace 里看到每一步做了什么，而不是只能看到最后一段回答。

## 4. MindBridgeAgent 接口定义了最小抽象

项目没有把 agent 抽象得很玄。所有内部 agent 都实现同一个接口：

```java
public interface MindBridgeAgent {
    AgentName name();
    boolean supports(AgentContext context);
    AgentDecision act(AgentContext context);
}
```

`name()` 用于记录当前 agent 的身份。`supports()` 用于判断当前上下文是否该由这个 agent 接手。`act()` 执行业务动作，更新上下文，并返回一个 `AgentDecision`。

`AgentDecision` 也很克制，里面只有三项：这一步做了什么动作，观察结果是什么，本轮 loop 是否完成。动作枚举包括读取记忆、意图路由、知识检索、风险评估和回复规划。每一步都会被包装成 `AgentStep`，最后通过 `AgentRunTraceService` 落库。

这套抽象的价值在于简单。它没有引入复杂的 agent 框架，也没有让每个 agent 自己决定下一步调用谁。调度权留在运行时，专家 agent 只处理自己的小任务。对于心理安全场景，这种朴素设计反而更可靠。

## 5. MemoryAgent 负责让系统“记得刚刚发生过什么”

`MemoryAgent` 是每轮对话的第一步。它先尝试从 Redis 读取当前会话的短期记忆。如果 Redis 里没有，说明短期缓存可能过期了，它会从 MySQL 的长期聊天记录里取最近消息，并刷新回 Redis。

短期记忆不是无限保留。`ShortTermMemoryService` 会根据配置只保存最近 N 轮上下文，并设置过期时间。完整消息仍然存在 MySQL 里，Redis 只是为了让当前对话更快拿到最近上下文。

除了会话历史，`MemoryAgent` 还会读取用户画像记忆。`UserProfileMemoryService` 会从学生输入中提取稳定、后续有用的信息，比如偏好、沟通方式、支持需求、个人背景和反复出现的状态模式。这些记忆会写入关系库，便于审计，也会镜像到 Chroma 做语义召回。

这里有一个重要边界：用户画像记忆不是诊断档案。抽取器明确要求不要保存诊断结论、风险等级、手机号、学号、证件号、真实姓名、详细地址或一次性任务。候选记忆还要经过置信度、长度和敏感内容过滤，最多保留 40 条。

最后，`MemoryAgent` 会把最近历史和用户画像整理成 `memoryBrief`。这段摘要会进入后续 agent 的上下文，但它不会把后台风险等级或诊断标签暴露给学生。它的作用是让系统少一点健忘，多一点连续性。

## 6. SupervisorAgent 负责先分清“这是不是心理问题”

`SupervisorAgent` 的职责很直接：把当前输入路由到 `CHAT`、`CONSULT` 或 `RISK`。

项目没有完全依赖模型做分类。`IntentClassifier` 先看高风险词库，如果出现明显自伤、轻生、伤人等表达，直接归为 `RISK`。这类信号优先级最高，不会被普通任务规则覆盖。

接着系统会识别明确的普通任务词，比如编程、作业、论文、翻译、总结、接口、bug 等。如果用户是在问学习、课程、项目或日常问题，并且没有心理求助信号，就走 `CHAT`。这个规则很实用，因为校园助手很容易遇到普通学习问题，不能每次都把“压力”“作业”“室友”之类的话题自动推向心理评估。

只有在词库和普通任务规则不能直接判断时，系统才调用模型分类。模型分类失败时，系统还会用咨询关键词和最近上下文做兜底。也就是说，Supervisor 的判断是“规则优先，模型补充，失败可降级”。

一旦结果是 `CHAT`，`SupervisorAgent` 会直接把 `knowledgeHandled` 和 `riskAssessed` 标成完成。这样普通聊天不会查 RAG，也不会生成心理报告。这个小动作背后其实是很重要的产品判断：心理关怀系统要敏感，但不能过度敏感。

## 7. KnowledgeAgent 只在需要时检索知识库

`KnowledgeAgent` 只处理 `CONSULT` 和 `RISK`。普通 `CHAT` 不会进入 RAG。这一点避免了两类问题：一是把正常聊天变成咨询场景，二是把知识库内容硬塞进不相关的问题里。

进入知识链路后，`KnowledgeAgent` 会先让模型把当前输入和记忆摘要改写成适合检索的中文 query。这个 query 不超过 40 个字，重点放在心理支持、校园求助流程、风险处理或情绪调节知识上。之后它调用 `KnowledgeService.retrieve()` 检索项目知识库。

检索不是单一路线。项目采用数据库主存储、可选 Chroma 向量索引、本地 embedding 兜底和 BM25 关键词检索混合的方式。Chroma 可用时优先查 Chroma，Chroma 没结果或不可用时尝试本地 embedding，相比之下 BM25 始终可以提供关键词兜底。检索结果会按向量分数和 BM25 分数融合，再进入 reranker。

`KnowledgeReranker` 会把候选片段交给当前大模型重新打分，判断每个片段对心理支持、校园求助流程或风险安全策略的帮助程度。模型不可用或输出解析失败时，reranker 会退回初排结果，不让检索链路因为二阶段排序失败而中断。

如果第一次检索结果不足，`KnowledgeAgent` 还会让模型生成一个更具体的 query 进行二次检索。最终命中的最佳片段会向前后邻居扩展一段，减少切块边界造成的信息断裂。这个细节很工程化，也很有用，因为心理支持类知识往往不是单句就能讲完整。

## 8. RiskGuardianAgent 把安全判断从自由生成里拿出来

`RiskGuardianAgent` 是心理安全链路里最不能省的一步。它不负责安慰学生，也不负责生成最终回复。它只做后台心理状态评估，并把风险等级写入上下文。

评估服务同样不完全依赖模型。`PsychologicalAssessmentService` 先检查高风险词库。如果出现明确危险信号，直接返回高风险，置信度设为 0.95。没有命中硬规则时，再调用模型输出严格 JSON，包括情绪标签、情绪分数、风险等级、置信度和一句判断依据。

模型输出解析后还会被归一化。风险等级会取模型等级和分数推导等级中更高的一方，降低低估风险的概率。如果模型调用失败或输出格式异常，系统会走关键词启发式兜底，比如焦虑、失眠、压力、低落、崩溃等词会触发相应评估。

还有一个细节：如果 `SupervisorAgent` 已经把意图判断为 `RISK`，但模型评估结果没有给到 `HIGH`，`RiskGuardianAgent` 会把风险提升为 `HIGH`。这相当于给路由层的高风险判断更高优先级。心理安全场景宁愿多保护，也不能把明显危险信号交给模型的偶然输出。

这些后台评估不会直接展示给学生。学生端不会看到风险等级、心理报告、评估分数或后台标签。它们服务于报告、预警和回复约束，而不是用来给学生贴标签。

## 9. CompanionAgent 保持普通助手体验

`CompanionAgent` 负责 `CHAT` 分支。它面向学习、生活、校园事务、编程和普通闲聊，不生成后台心理报告。

它会先让模型制定一句简短回复策略，要求不要做心理评估，不要输出风险等级，不要替用户下诊断。然后它组装最终消息，把普通聊天模式的 system prompt、记忆摘要、回复策略和对话历史一起交给模型流式输出。

这个 agent 的存在很重要。没有它，所有输入都容易被统一塞进心理支持 prompt，用户问一个 Java bug，系统也可能开始温柔追问“你最近是否压力很大”。这会让产品变得奇怪，也会损害学生对系统的信任。

MindBridge 的普通聊天提示词明确要求：对编程、学习、事实查询、校园事务等普通问题，回答完只围绕原问题延展，不要主动追问心理状态，不要把普通聊天强行引导成心理咨询。这个边界让系统更像一个能识别场合的校园助手。

## 10. CounselorAgent 负责心理支持回复规划

`CounselorAgent` 处理 `CONSULT` 和 `RISK` 分支。它会结合 `MemoryAgent` 的记忆摘要、`KnowledgeAgent` 的检索结果和 `RiskGuardianAgent` 的评估摘要，生成心理支持式回复策略。

它的策略不是诊断，也不是报告。prompt 明确要求不要直接给诊断，不要输出后台标签、风险等级、分数或报告口吻。高风险时，策略必须优先保护学生安全。

在最终消息里，`CounselorAgent` 会把知识库命中的内容整理成系统上下文。回答 prompt 要求模型优先基于检索知识回答，知识不足时要说明，不要编造心理学术语、流程或数据。高风险时还会注入专门规则：先回应情绪，把重点放在当前安全上，鼓励学生立刻联系可信任的人、学校辅导员、心理中心或当地紧急救助，不提供任何危险操作细节。

这说明本项目里的心理支持不是靠模型临场发挥。模型可以生成有温度的语言，但可用知识、禁止输出、风险处理顺序和学生端展示边界都由系统提前约束。

## 11. RAG 在这里不是外挂，而是 agent 流程的一部分

很多项目把 RAG 做成“问之前查一下库”。MindBridge 的 RAG 更谨慎，它先经过 Supervisor 路由，再由 KnowledgeAgent 改写 query、检索、判断结果是否足够、必要时二次检索，最后由 CounselorAgent 注入回复上下文。

内置知识库位于 `src/main/resources/knowledge/`，包括校园心理健康、风险策略、焦虑睡眠、低落社交、学业压力、校园求助、人际家庭冲突、危机安全计划、隐私边界等 Markdown 文档。管理员也可以通过接口追加文本或上传 PDF、Markdown、txt 文件。

知识入库时会切块、写入 `knowledge_chunks` 表，并在有配置时生成 embedding 和镜像到 Chroma。数据库是主存储，Chroma 是可重建的索引层。这个设计让系统在向量服务不可用时还能工作，也让后台知识内容有稳定来源。

RAG 还有评测链路。项目可以导出 RAGAS 所需的评测报告，把检索上下文、回答、参考答案和期望意图等信息交给 `eval/` 下的 Python 工具评估。它不是只做功能演示，而是给知识检索质量留下了可量化检查的入口。

## 12. 记忆系统和 RAG 是两条不同的线

项目里有两种“召回”。一种是知识库 RAG，服务的是心理支持知识、校园资源和风险策略。另一种是用户画像召回，服务的是个体化对话。

知识库回答“遇到焦虑失眠可以参考什么步骤”“危机场景应该怎样处理”“学校求助资源怎么组织”。用户画像回答“这个学生之前说过自己更喜欢直接一点的建议”“他最近反复提到考试压力”“她希望先听简短步骤再展开”。

这两条线不能混在一起。知识库内容可以被管理员维护和替换，用户画像则属于某个学生，需要脱敏、过滤、审计和删除能力。MindBridge 把它们分成不同服务、不同集合和不同使用位置，是比较清醒的设计。

## 13. 工具链放在回复之后，减少对学生端体验的干扰

当一轮对话被判断为 `CONSULT` 或 `RISK`，并且已经生成心理评估后，系统会保存 `PsychologicalReport`。报告里包含用户、会话、原始内容、意图、情绪标签、情绪分数、风险等级、置信度和摘要。

学生端回复完成后，`ToolOrchestrationService` 才异步执行后台工具链。顺序是先写 Excel，写入成功后，如果风险等级是 `HIGH`，再给配置的收件人发送预警。每个收件人有独立重试和落库状态，管理员后台可以看到最终结果。

工具实现也不是单一路径。Excel 可以本地写文件，也可以通过 HTTP 或 MCP 工具调用。预警可以写日志、SMTP 发送、HTTP 调用或走 MCP Server 暴露的工具。这个设计让本地演示、课程答辩、真实部署可以用不同配置切换，不需要改主流程代码。

更重要的是，工具链失败不会中断学生正在进行的对话。异常会写入报告状态和错误信息，但不会把后台失败直接抛到学生端。心理支持场景里，学生端的连续回应要优先保持稳定。

## 14. 可观测性让 agent 不再是黑箱

每一轮 agent loop 都会被保存为 `AgentRunTrace`。概要字段包括输入、意图、风险等级、记忆摘要、知识 query、回复策略、负责回复的 agent、开始和完成时间、步骤数量。每个 `AgentStep` 还会记录 step number、agent 名称、动作、观察结果和时间。

这套 trace 对项目展示很有价值。管理员或开发者可以看到某一次对话为什么被路由为 `CONSULT`，KnowledgeAgent 用了什么 query，检索到了多少条结果，RiskGuardianAgent 判断的风险和情绪是什么，最终由哪个回复 agent 接手。

对心理健康系统来说，可观测性不是锦上添花。它关系到安全复盘、误判排查和后续优化。如果某次普通学习问题被误判成咨询，可以看 Supervisor 的判断依据和历史上下文。如果某次高风险没有触发预警，可以顺着 trace、report、Excel 状态和 alert 状态一路查下去。

## 15. 这个 agent 范式背后的工程取舍

MindBridge 的 agent 范式不是为了展示“多 agent”这个概念本身。它解决的是几个具体问题。

第一，职责拆分。记忆、路由、检索、风险、回复是五类不同工作。拆开以后，每个模块更容易测试、替换和解释。

第二，安全边界。风险判断不放在最终回复里临时处理，而是提前进入独立 agent 和后台评估服务。高风险词库、JSON 解析、分数归一化、关键词兜底一起降低漏判概率。

第三，体验边界。普通聊天不进入心理链路，咨询和风险才进入 RAG 与评估。这样既保护学生，也避免系统把所有问题都说成心理问题。

第四，降级能力。Redis 不可用可以读 MySQL，Chroma 不可用可以走 embedding 或 BM25，reranker 失败可以退回初排，模型评估失败可以走关键词启发式，工具链失败也不会打断学生端回复。

第五，审计能力。Agent trace、心理报告、用户画像记忆、Excel 状态和预警状态都能落库。项目不是只留下“模型回答了什么”，还留下“系统如何走到这个回答”。

这些取舍让 MindBridge 更像一个能部署、能解释、能复盘的系统。它当然可以聊天，但真正的价值在于后台那套看得见、查得到、能降级的运行机制。

## 16. 和单 prompt 架构相比，它强在哪里

如果只用一个大 prompt，也能写出一个看起来温柔的心理陪伴机器人。但问题会出在边界上。模型既要判断意图，又要记忆用户，又要检索知识，又要做风险评估，还要生成最终回复。所有要求混在一起，prompt 越写越长，行为越难预测。

MindBridge 把这些要求拆成多个阶段。分类 prompt 只分类，不回答。心理评估 prompt 只输出 JSON，不安慰。KnowledgeAgent prompt 只改写 query 和判断检索充分性。CompanionAgent 和 CounselorAgent 才处理最终回复。每个 prompt 更短，任务更窄，结果也更容易检查。

单 prompt 架构还有一个问题：很难知道哪里错了。回答不好时，到底是记忆错了、路由错了、检索错了、风险评估错了，还是最终生成错了？多 agent 结构至少把排查路径拆开了。trace 里每一步都有名字和 observation，这对迭代很重要。

## 17. 扩展新 agent 的方式

这个范式的扩展点也很清楚。如果将来要加入新的能力，比如“校园资源预约 Agent”“咨询师转介 Agent”“长期趋势分析 Agent”“家校协同提醒 Agent”，不需要推翻现有结构。

新增 agent 需要做三件事。第一，实现 `MindBridgeAgent` 接口。第二，在 `supports()` 里定义它何时接手。第三，在 `AgentRuntimeService` 的 agent 列表里放到合适顺序。必要时再给 `AgentContext` 增加字段和标记位。

不过这个项目也提醒我们，agent 不是越多越好。每新增一个 agent，都会增加状态、trace、测试和误判路径。比较稳妥的原则是：只有当一个职责需要独立数据、独立模型调用、独立工具权限或独立审计时，才值得拆成 agent。否则留在已有 agent 里会更简单。

## 18. 一句话总结

MindBridge 的 agent 范式可以概括为：用有限步状态机组织多个专家 agent，让模型在可控边界内完成记忆整理、意图路由、知识检索、风险评估和回复规划；普通聊天保持轻量，心理咨询进入 RAG，高风险场景优先安全，后台全过程可记录、可审计、可降级。

它的重点不在“让 AI 自主行动”，而在“让 AI 的每一步都有岗位、有边界、有记录”。这正是校园心理健康项目需要的智能体形态。
