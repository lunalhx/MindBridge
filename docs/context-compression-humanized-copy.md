# MindBridge 上下文压缩文案

## 草稿

MindBridge 的上下文压缩不是把一段聊天历史简单总结成几句话。它更像一套分层的上下文管理流程：当前输入先脱敏，最近历史保留在 Redis 窗口里，长期信息被抽成用户画像，心理知识库被切块、检索和重排，风险评估结果只进入后台控制和回复策略。最后进入模型的内容，是这些信息经过筛选后的组合。

这个设计服务于校园心理陪伴场景。学生希望系统记得自己说过什么，但又不希望每一句隐私表达都被长期塞进模型。辅导员需要看到完整会话和风险记录，学生端回答却不能暴露风险等级、诊断标签和后台报告。项目用 Agent loop 把这些职责拆开：MemoryAgent 读记忆，SupervisorAgent 分流意图，KnowledgeAgent 找知识，RiskGuardianAgent 做风险守护，CompanionAgent 或 CounselorAgent 负责最终回复。

上下文压缩在项目里有几种具体形态。第一是窗口压缩，系统只保留最近若干轮消息给模型。第二是摘要压缩，MemoryAgent 把最近历史压成 1 到 3 条要点，用户画像服务把稳定偏好和支持需求写成短句。第三是检索压缩，KnowledgeAgent 把当前输入改写成短 query，KnowledgeService 只取少量知识片段。第四是安全压缩，PrivacySanitizer 会替换手机号、学号、证件号和姓名表达，PromptTemplates 会把后台风险判断转成安全规则。

这样做的好处是模型不需要看到系统掌握的全部信息。它看到的是当前问题、最近窗口、memoryBrief、少量知识片段和回复策略。这样既保留连续性，也控制长度和隐私风险。

# MindBridge 是怎么做上下文压缩的

MindBridge 里的“上下文压缩”，不能只理解成“把聊天记录总结一下”。如果只做摘要，这个项目很快会碰到三个问题。

第一，心理陪伴场景里的上下文很杂。它不只有聊天历史，还包括用户画像、校园心理知识库、意图判断、风险评估、回复策略、Agent 运行状态，以及后台审计需要保留的原始记录。

第二，所有上下文都塞给模型并不安全。学生可能输入手机号、学号、真实姓名，也可能说出很私密的情绪状态。系统需要记住对回复有帮助的内容，但不能把所有敏感细节都放进模型提示词。

第三，模型上下文窗口不是数据库。数据库可以保存完整会话，模型只应该看到本轮回答需要的那一小部分材料。MindBridge 的做法就是把这三件事拆开：该保存的保存，该压缩的压缩，该隐藏的隐藏，该进入 prompt 的才进入 prompt。

## 一句话说明

MindBridge 的上下文压缩，是“短期窗口 + 长期画像 + RAG 检索 + 安全脱敏 + Agent 状态机”的组合。

短期窗口负责保留最近对话。长期画像负责记住稳定偏好和支持需求。RAG 检索负责从心理知识库里拿少量相关片段。安全脱敏负责挡掉常见身份标识。Agent 状态机负责决定这些信息什么时候被读取、什么时候被压缩、什么时候进入最终回答。

最后送给模型的不是完整历史，而是一份整理过的上下文包：当前输入、最近若干条历史、`memoryBrief`、必要的知识库片段、回复策略，以及不直接展示给学生的安全约束。

## 项目里的上下文到底包括什么

在普通聊天系统里，上下文常常就是“最近几轮聊天”。MindBridge 不一样。它是校园心理健康陪伴系统，所以上下文至少分成六类。

第一类是当前请求。也就是学生本轮输入、当前会话、当前用户，以及脱敏后的模型输入。`ChatService.prepare()` 会保留原始输入，同时调用 `PrivacySanitizer.sanitize()` 生成 `modelInput`。原始输入用于落库和后台回看，脱敏后的输入给模型和 Agent 使用。

第二类是最近会话历史。完整消息写在 `chat_messages` 表里，最近窗口放在 Redis list 里。Redis key 的格式是 `mindbridge:chat:short-memory:{sessionId}`。每次保存用户消息或助手回复，`ChatService.saveMessage()` 都会顺手写入短期记忆。

第三类是长期用户画像。它不是完整聊天记录，而是从对话里抽取出来的稳定信息，比如“用户更喜欢直接一点的建议”“用户提到自己不太敢主动联系辅导员”“用户最近多次提到睡眠问题”。这些内容由 `UserProfileMemoryService` 管理，保存在 `user_memory_items` 表里，也可以同步到 Chroma 做语义召回。

第四类是知识库上下文。校园心理知识、危机处理流程、求助渠道和情绪调节建议会被切成 `KnowledgeChunk`。咨询和风险场景下，系统才会检索这些片段，并把少量命中内容放进回答 prompt。

第五类是风险和情绪上下文。`RiskGuardianAgent` 和 `PsychologicalAssessmentService` 会结合当前输入和最近历史做后台评估。这个评估用于决定回复边界、是否生成报告、是否触发后续工具链，但不会直接原样告诉学生。

第六类是 Agent 运行状态。`AgentContext` 保存本轮对话中各 Agent 产生的中间结果，包括 `memoryBrief`、`intent`、`knowledgeQuery`、`retrievedKnowledge`、`riskLevel`、`responsePlan`、`responseMessages` 和步骤记录。它只在本轮请求内存在，跨轮复用靠 Redis、MySQL、用户画像和知识库索引。

## 一轮对话里，上下文怎么流动

一次聊天从 `/api/chat/stream` 进来。`ChatService` 先拿到用户输入，去掉首尾空白，然后生成两份文本：`originalInput` 和 `modelInput`。前者是真实原文，后者经过脱敏。

接下来，`AgentRuntimeService.run()` 创建一个 `AgentContext`，把用户、会话、原始输入和模型输入放进去。然后系统开始有限步 Agent loop。它最多走 8 步，不是那种无限自主循环。

Agent 的顺序是固定的：`MemoryAgent`、`SupervisorAgent`、`KnowledgeAgent`、`RiskGuardianAgent`、`CompanionAgent` 或 `CounselorAgent`。每个 Agent 都通过 `supports(context)` 判断自己是否该接手。做完自己的事，就更新 `AgentContext` 里的字段和标记位。

这里有个小细节很重要：Agent loop 运行时，本轮用户消息还没有保存到数据库。也就是说，MemoryAgent 从 Redis 或 MySQL 读到的是“本轮之前”的历史。为了不丢当前问题，它会把脱敏后的 `modelInput` 手动追加到 `modelHistory` 里，再按配置裁剪窗口。

Agent loop 结束后，`ChatService` 才保存用户消息、保存 trace、更新用户画像、必要时生成心理报告。真正的学生端回答随后通过 `aiClient.stream()` 以 SSE token 形式输出。助手回复流式生成完以后，系统再把助手消息保存到数据库和 Redis。所以下一轮对话才能读到这次回复。

这个顺序听起来绕，但它解决了两个问题：当前输入不会在本轮模型上下文里丢失，数据库里的完整会话也不会被半截流式回复污染。

## 第一层压缩：短期记忆窗口

短期记忆由 `ShortTermMemoryService` 实现，底层是 Redis list。它保存的不是无限历史，而是最近窗口。

默认配置里，`CHAT_HISTORY_LIMIT` 是 10。代码里会把它理解成“轮次”，再乘以 2，保留用户和助手两侧消息。所以默认情况下，模型最多拿到最近 20 条消息。Redis 里也是同样的窗口。

每次追加消息时，服务会做三步。先 `rightPush` 新消息，再用 `trim` 裁到最近窗口，最后设置过期时间。默认 `CHAT_SHORT_MEMORY_TTL_HOURS` 是 24 小时。

这就是最基础的上下文压缩：不让会话历史无限增长。

它的好处很直接。模型输入不会越来越长，Redis 占用不会跟着会话长度一直涨，普通用户也更容易理解“保留最近 10 轮”这种配置。

Redis 不是唯一来源。如果 Redis 里没有历史，MemoryAgent 会从 MySQL 读取最近 20 条聊天消息，按时间正序恢复，并刷新 Redis。这样 Redis 过期、重启或临时不可用时，系统还能从长期聊天记录里找回最近上下文。

项目还做了一个稳妥的降级：Redis 读写失败只打 debug 日志，不打断聊天。心理陪伴场景里，偶尔少一点短期记忆，比整个聊天接口挂掉要好。

## 第二层压缩：脱敏后的模型历史

短期记忆不是直接原样进入模型。MemoryAgent 会把 Redis 或数据库里的消息转成 `AiMessage`，转换时调用 `PrivacySanitizer.sanitize()`。

目前脱敏规则覆盖几类常见标识：手机号、学号、证件号，以及“我叫某某”“我是某某”这类姓名表达。它不是完整的数据防泄漏系统，但能挡住校园场景里最常见的身份信息。

这一步很实际。数据库可以保留原文，方便管理员回看和审计；模型侧只拿脱敏后的语义。也就是说，同一句话在系统里有两种用途：原文用于记录，脱敏文本用于推理。

## 第三层压缩：memoryBrief

`memoryBrief` 是 MindBridge 里最像“上下文压缩成品”的东西。它不是完整历史，也不是纯画像，而是用户画像摘要和最近对话摘要的合并结果。

用户画像摘要来自 `UserProfileMemoryService.profileBrief()`。系统会按当前输入召回用户相关的画像条目，最多放入 8 条。每条都是短句，比如偏好、沟通方式、支持需求、个人背景或状态模式。

最近对话摘要来自 `MemoryAgent.summarizeMemory()`。它会把最近历史交给模型，让模型只输出 1 到 3 条中文要点。Prompt 明确要求不要输出风险等级、诊断结论或后台标签。如果历史和当前输入没关系，就输出“无相关历史记忆。”。

这里还有两道长度控制。第一，摘要用到的历史只取最近 12 条消息。第二，摘要结果最长保留 400 字。

合并时，MemoryAgent 会判断两部分是否为空。如果画像和历史都有，就输出两段：“用户画像”和“最近对话记忆”。如果只有一部分，就只保留那一部分。如果都没有，就统一返回“无相关历史记忆。”。

这个统一默认值看起来不起眼，但对后续 Agent 很方便。后面的 Agent 不需要处理一堆 null、空字符串或异常结构，直接读 `memoryBrief` 就行。

`memoryBrief` 后面会被多次使用。KnowledgeAgent 用它改写检索 query，CompanionAgent 用它规划普通聊天回复，CounselorAgent 用它制定心理支持策略。它不是替代历史窗口，而是和历史窗口一起工作。窗口保留最近原话，brief 提供更高密度的线索。

## 第四层压缩：长期用户画像

长期记忆如果直接存完整聊天，会很危险，也很难解释。MindBridge 选择了另一条路：只把对后续有稳定帮助的信息抽成画像条目。

每轮用户消息保存后，`ChatService.rememberUserProfile()` 会调用 `UserProfileMemoryService.rememberUserInput()`。服务先脱敏输入，太短的输入直接跳过。然后模型根据本轮输入和已有 `memoryBrief` 抽取候选记忆。

抽取范围被限制得很窄，只包括五类：用户偏好、沟通风格、支持需求、个人背景、反复出现的状态模式。Prompt 明确要求不要保存诊断结论、风险等级、手机号、学号、证件号、真实姓名、详细地址，也不要保存一次性的临时任务。

模型必须返回 JSON 数组。每个候选包含 `type`、`summary`、`evidence` 和 `confidence`。服务端还会继续过滤：置信度低于 0.55 的丢掉，摘要太短或太长的丢掉，摘要里出现敏感占位符、诊断表达或风险等级的也丢掉。

如果模型抽取失败，系统只对非常明确的偏好句做兜底，比如“请记住”“我喜欢”“以后不要”。这样不会因为模型异常就乱存记忆。

写入时使用 upsert。系统按记忆类型和归一化摘要查重，已有条目就刷新证据、置信度和时间，没有就新增。每个用户最多保留 40 条，超过后删除较旧条目，并同步删除对应 Chroma 索引。

召回时，系统优先用 Chroma 按当前输入查询用户自己的画像，查询带 `userId` 过滤。Chroma 只负责召回 id，最终还要回数据库取完整实体。如果 Chroma 没返回结果，就回退到数据库最近更新的 12 条。

这个设计的取舍很清楚。它没有把所有历史消息都向量化后随便召回，而是把长期记忆做成可审计的短条目。它可能丢掉一些细节，但更可控。对心理陪伴产品来说，这个取舍挺合理。系统应该记住“用户希望建议更具体”，而不是把用户某天深夜的整段倾诉永久放进 prompt。

## 第五层压缩：RAG 知识库

心理知识库也需要压缩。知识库文档不可能整篇塞进模型，只能先切块，再检索，再筛选。

入库时，`KnowledgeChunker` 会先统一换行并去掉首尾空白，然后按配置切分文本。默认 `KNOWLEDGE_CHUNK_SIZE` 是 512，`KNOWLEDGE_CHUNK_OVERLAP` 是 64。代码里还做了保护：chunk size 至少 120，overlap 不超过 chunk size 的一半。

切分时，系统优先在自然边界断开，比如换行、中文句号、英文句号和问号。找不到合适边界时，才按固定长度切。这样可以减少“一个求助流程被切成前后两半”的问题。

检索时，KnowledgeAgent 不直接用学生原话搜知识库。它会结合 `memoryBrief` 和当前输入，把问题改写成不超过 40 字的中文 query。学生原话可能很长，也可能夹杂情绪、背景和口语表达。短 query 更适合检索。

`KnowledgeService.retrieve()` 采用混合召回。向量检索优先走 Chroma，Chroma 没结果时回退到本地 embedding 余弦相似度。同时，BM25 会在数据库 chunk 上做关键词召回。两路结果合并时，向量权重是 0.65，BM25 权重是 0.35。

混合召回后还有 reranker。`KnowledgeReranker` 会把候选片段交给模型重新打相关性分数。默认最多处理 20 个候选，每个 chunk 送入 reranker 的内容最多 700 字。最终分数按 0.85 的重排分和 0.15 的初排分合成。

如果 reranker 失败，系统回退到初排结果，不让知识检索链路被一个模型调用拖垮。

最终进入回答 prompt 的结果数量由 `RAG_TOP_K` 控制，默认是 4。项目还对排名第一的命中做了邻居扩展：找到最佳 chunk 后，把同一 source 下前一块、当前块、后一块拼起来。其他命中保持原样。

这也是一种很具体的压缩策略。最相关的片段值得补上下文，其他片段就别扩太多。否则每条命中都带前后邻居，prompt 很快会变胖。

## 第六层压缩：意图分流

MindBridge 不是每轮都走完整心理链路。`SupervisorAgent` 会先做意图分类，把输入分成 `CHAT`、`CONSULT` 和 `RISK`。

普通学习、编程、课程、论文、校园事务、日常闲聊都尽量留在 `CHAT`。只有明确心理求助、情绪困扰、压力、焦虑、低落、失眠等内容才进入 `CONSULT`。出现自伤、自杀、伤人或即时危险信号时进入 `RISK`。

这其实也是上下文压缩。因为普通聊天不需要 RAG 知识库，不需要心理评估，也不需要风险报告。系统通过意图分流，直接减少不必要的上下文和中间状态。

更重要的是，它避免把学生所有问题都心理化。一个学生问代码、问论文、问课程安排，系统就正常回答，不要强行追问“你是不是有情绪困扰”。这一点对产品体验很重要。

## 第七层压缩：风险信息只进入控制规则

风险评估结果不能直接当成学生端内容。项目里，`PsychologicalAssessmentService` 会输出情绪、情绪分数、风险等级、置信度和摘要。这些信息会进入后台报告和回复规划，但 `PromptTemplates.answerSystemPrompt()` 明确禁止向学生输出风险等级、心理报告、评估分数或后台判断标签。

高风险时，系统 prompt 会加入高风险处理规则。规则要求先回应情绪，再关注当前安全，鼓励联系身边可信任的人、学校辅导员、心理中心或当地紧急救助，并禁止提供危险操作细节。

也就是说，风险上下文被“压缩”为回复边界和安全规则，而不是被原样展示。

这个处理很必要。学生需要的是支持和下一步行动，不是被模型贴上“高风险”标签。

## 最终 prompt 是怎么组装的

Agent loop 不直接生成完整回答。它先生成回复策略，再把最终消息交给 `aiClient.stream()`。

普通聊天走 `CompanionAgent`。它先根据当前输入和 `memoryBrief` 生成一句简短回复策略，然后构造回答消息：CHAT 模式 system prompt、包含记忆摘要和回复策略的 system message、裁剪后的 `modelHistory`。

心理咨询和风险场景走 `CounselorAgent`。它的策略输入更多，包括 `memoryBrief`、当前输入、风险守护摘要、知识库 query 和知识库命中。最终回答消息里会包含 CONSULT 或 RISK 模式 system prompt、RAG 知识上下文、记忆摘要、检索 query、回复策略和 `modelHistory`。

如果 Agent 生成的 `responseMessages` 为空，`ChatService.buildMessages()` 还有兜底逻辑。它会把检索片段作为系统上下文，再按 `historyLimit * 2` 控制历史窗口。

所以最终 prompt 不是粗暴拼接，而是按用途组装。模型看到的内容大致是这几部分：任务规则、必要知识、记忆摘要、回复策略、最近历史、当前输入。

## 审计：压缩以后还能不能查

上下文压缩有个副作用：回答出问题时，很难一眼看出是哪一步错了。是历史没读到，还是摘要压错了，还是 query 改偏了，还是知识片段召回不够，还是风险判断误判？

MindBridge 用 `AgentRunTraceService` 记录每轮 Agent loop。trace 会保存用户、会话、触发消息、原始输入、意图、风险等级、`memoryBrief`、`knowledgeQuery`、`responsePlan`、负责回复的 Agent、步骤数和时间信息。

每一步 Agent 的动作也会保存。例如 MemoryAgent 会记录从 Redis 还是 MySQL 加载了多少条消息，KnowledgeAgent 会记录 query 和召回数量，RiskGuardianAgent 会记录风险等级和情绪标签。

它没有保存完整 prompt，这对隐私更稳。但它保存了排查最需要的中间产物。开发者可以沿着 trace 看：记忆有没有读到，brief 是否靠谱，知识 query 是否跑偏，最后是谁负责回复。

## 配置怎么控制上下文大小

上下文压缩不是写死的，主要由 `mindbridge` 配置控制。

`CHAT_HISTORY_LIMIT` 默认 10，决定模型侧保留多少轮历史。服务层会乘以 2，保留用户和助手两侧消息。

`CHAT_SHORT_MEMORY_TTL_HOURS` 默认 24，决定 Redis 短期记忆多久过期。

`MEMORY_TOP_K` 默认 6，决定每轮按当前输入召回多少条用户画像。

`RAG_TOP_K` 默认 4，决定最终进入回答上下文的知识片段数量。

`RAG_RERANKER_CANDIDATE_LIMIT` 默认 20，决定初排后最多交给 reranker 的候选数。

`RAG_RERANKER_MAX_CONTENT_CHARS` 默认 700，决定单个 chunk 送入 reranker 的最大字符数。

`KNOWLEDGE_CHUNK_SIZE` 默认 512，`KNOWLEDGE_CHUNK_OVERLAP` 默认 64，决定知识库切块的粒度。

`AI_MAX_TOKENS` 默认 512，控制学生端单次回复的最大生成长度。

这些配置分别控制历史、画像、知识和输出。调参时不能只看一个值。比如 `RAG_TOP_K` 变大，知识更全，但 prompt 也更长，模型可能更分心。`CHAT_HISTORY_LIMIT` 变小，延迟和成本会降，但连续性可能变差。

## 这套方案的取舍

当前实现没有精确 token 预算。它主要用消息条数、字符数、topK 和最大输出 token 控制上下文。这种方式简单、好调，也方便解释。但如果未来接入上下文窗口差异很大的模型，就需要增加 token 估算。

项目也没有做会话级滚动摘要。`memoryBrief` 是每轮临时生成的，trace 会保存当轮结果，但下一轮不会直接读取上一轮 brief。长期连续性主要靠用户画像承接。这样更可控，但长对话里的叙事线索可能会丢。

原始聊天历史没有全量语义检索。系统不会把所有历史消息向量化后按当前输入召回，而是依靠最近窗口和画像条目。这降低了隐私风险和误召回风险，但如果很久以前的重要背景没有被抽成画像，后面可能找不回来。

用户画像依赖模型抽取。服务端有过滤和上限，但模型仍可能把一次性情绪误存为长期模式。心理状态类画像尤其需要谨慎，最好后续增加过期策略和用户可编辑能力。

RAG 只扩展第一条最佳命中。这个策略能控制 prompt 长度，也能修复最重要片段的边界问题。但如果第二或第三条命中也处在文档流程中间，模型看到的内容可能还是不完整。

这些取舍不是缺陷清单，更像当前版本的边界。它已经能支撑一个可用、可审计、可降级的校园心理陪伴系统，但还没有做到精细 token 编排和长期叙事记忆。

## 后续可以怎么加强

可以先做 token 预算器。预算器按模型上下文窗口，把 system prompt、memoryBrief、RAG 片段、历史窗口和当前输入分配预算。超出预算时，先压缩历史，再减少低分知识片段，最后裁剪画像摘要。

可以增加会话级滚动摘要。每轮结束后，把旧历史合并进一个可审计的 session summary。下一轮先读 summary，再读最近窗口。这样长对话不会只剩最近几轮。

可以给用户画像加生命周期。偏好类记忆可以保存久一点，状态模式类记忆应该更容易过期，也应该让用户能查看、修改和删除。

可以记录最终 prompt 的结构化调试视图。重点不是保存完整敏感文本，而是保存各部分长度、来源、chunk id、分数、是否被截断。这样排查上下文问题会更快。

可以让 RAG 邻居扩展更动态。比如只对高分命中扩展相邻块，或者根据标题、编号、列表结构判断是否需要扩展。这样比固定只扩第一条更细。

可以把 `memoryBrief` 改成结构化输出。现在它是自然语言文本，后续 Agent 只能整体读。结构化以后，可以区分稳定画像、最近事件、用户偏好、安全相关但不可展示的信息，让不同 Agent 按需使用。

## 收束一下

MindBridge 的上下文压缩不是一个单点功能，而是一条从输入到回答的处理链。

输入先脱敏。短期历史用 Redis 窗口控制长度。长期信息抽成用户画像。最近历史被压成 `memoryBrief`。知识库通过切块、混合召回、reranker 和 topK 收束。风险评估结果只进入后台报告和安全规则。最终 prompt 再由 CompanionAgent 或 CounselorAgent 按场景组装。

这套设计最值得讲的地方，不是“用了摘要”，而是它把上下文分了边界。完整会话属于审计，短期窗口属于连续对话，用户画像属于长期个性化，RAG 片段属于专业知识，风险评估属于后台安全控制，学生端回答只拿自己需要的那部分。

对校园心理陪伴来说，这个边界比单纯追求更长上下文更重要。因为系统不只是要回答得像懂用户，还要知道哪些内容该记住，哪些内容该压缩，哪些内容不该直接说出口。
